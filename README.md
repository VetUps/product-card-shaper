# Product Card Shaper

Прототип AI-сервиса для автоматической подготовки карточек контрольно-измерительных приборов (КИПиА) для B2B-интернет-магазина.

---

## Быстрый запуск

1. Создайте в корне проекта файл `.env` и укажите API-ключ:
   ```env
   API_KEY=ваш_ключ_api
   ```

2. Соберите и запустите контейнеры:
   ```bash
   docker compose up --build
   ```

3. Откройте в браузере:
   - **Веб-интерфейс:** [http://localhost:3000](http://localhost:3000)
   - **Swagger UI:** [http://localhost:8000/docs](http://localhost:8000/docs)

Остановка сервисов:
```bash
docker compose down
```

## Принятые решения

- **Навайбкоженный front:** так как задание скорее про проектирование и разработку backned части, было принято решение сделать frontend при помощи ИИ.
- **Двухуровневая валидация:** входной JSON проверяется до обращения к LLM, а ответ LLM валидируется по строгой схеме `ProductCard`.
- **Защита от галлюцинаций:** в системном промпте зафиксировано правило использовать только факты из входного JSON; отсутствующие базовые характеристики помечаются как `"данных нет"` и выносятся в `missing_or_unclear_fields`.
- **Реализация структурного ответа:** так как я использовал deepseek, обычный response_format с parse() методом тут не подошёл, так как у DeepSeek API тип json_schemа не подходит. Было принято решение отправлять схему в виде JSON, задав инструкцию возвращать ответ именно в виде этой схемы.
- **Ограничения и развитие:** если модель вернёт ответ, который не пройдёт Pydantic схем, то вернётся ошибка валидации - в продакшене это можно дополнить ретраями с корректировкой длины. Также, заложена база под большее количество одновременных запросов к LLM засчёт асинхронной API, и засчёт использования асинхронного клиента OpenAI.
